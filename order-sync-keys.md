# Order Sync Keys

**Purpose.** When analyzing an integration with a new e-commerce system, these are the vital data an order must carry to survive the round trip across the four systems: **sale channel → OMS → WMS → carrier**, and status flowing back. Focus the analysis on finding these keys in the new system's API payloads first — everything else is decoration.

**The core rule — dual-identifier handshake.** At every hop, the sender includes **its own reference**, the receiver assigns **its own ID** and returns it, and every later message between them (webhook, ship confirmation, cancel, COD remittance) carries **both IDs side by side**. If either side drops one of the two, correlation dies on the return leg. Property names below are common variants seen across real platforms; the new system will have its own name for each — the analysis job is to find it.

**JPluger columns (added 2026-08-08).** *JPluger Specs Property* = where the concept lives in the spec harness templates (`marketplace-integrations/specs/_templates` for Leg 1, `wms-integrations/specs/_templates` for Leg 2), as `<spec file>, <request|response> <property>`. Carrier (Leg 2/3 boundary, D2) has **no specs harness** → that column is N/A for Leg 3 and the DTO comes from `carrier-core` code. *JPluger DTO Property* = the verified Java DTO/entity field, as `DTO.property`. Confidence is inline per finding: **(A)** fits description + usage + name + data type · **(B)** fits the logic / similar meaning · **(C)** assumed from logic or the way it is used in code. `not found` = no canonical home exists in the templates/code (nothing inferred).

## Leg 2 — OMS ↔ WMS

| Vital data | Possible Property Name | Business Explanation | Why it's vital | JPluger Specs Property | JPluger DTO Property |
|---|---|---|---|---|---|
| **External order reference** | `reference_id`, `partner_order_id`, `external_order_id`, `reference_num` | The OMS's own order identifier, sent when pushing the order to the WMS. Must be unique (per account/channel) and immutable. | This is the echo key: the WMS returns it on every downstream event (ship confirm, cancel, exception), which is what lets the OMS join those events back to its order. | **WMS-assigned order/shipment ID** | `id`, `order_id`, `shipment_id` | The WMS's internal identifier, returned in the create-order response. | Some operations (cancel, amend, shipment lookup) only accept the WMS's own ID, not your reference. Capture it at creation or lose those operations. Beware: it may be **re-minted** on cancel/replace flows. | not found — the WMS create-order response is a per-integration `responseType`; no canonical template property | entity `WmsOrders.wmsOrderId` (B); `WmsOrderShipment.shipmentNumber` (B); generic link `WmsOrderReference.referenceId/referenceType` (C) |
| **Channel / source identity** | `channel_id`, `shop_name`, `store_id` | Which upstream sales channel or shop the order came from. | Scopes the external reference's uniqueness and routes ship confirmations back to the right upstream integration. | `EXAMPLE.IWmsOrderService.createOrder, request channel ← dataDTO.marketplaceCode` (A) | `orders.DataDTO.marketplaceCode` (A); `DataDTO.storeCode` (JSON `ss_code`) (B) |
| **Warehouse ID** | `warehouse_id`, `location_id`, `facility_id` | Which physical warehouse/fulfillment center handles the order (order- or line-level). | Multi-warehouse routing, and the second key (with SKU) for inventory sync. | **SKU per line** | `sku` | The product code the WMS resolves each order line against, by exact string lookup at ingest. | A SKU unknown to the WMS stops the order at the door (rejected or held). The whole chain works only if channel seller-SKU, OMS catalog SKU, and WMS SKU are the same string. | `EXAMPLE.IWmsOrderService.createOrder, request lines[].sku ← dataDTO.orderItems[].sellerSku` (A) | `orders.OrderItemDTO.sku` (A — note: the EXAMPLE's `sellerSku` path is illustrative; the real field is `sku`) |

| **Shipping method instruction** | `shipping_method`, `carrier`, `ship_option` | Which carrier/service the WMS should book or expect, expressed in a pre-agreed mapping. | An unmapped value fails order creation or ships on the wrong service; the mapping table is a standing artifact of the integration. | not spelled — the `requestMapping` for it is per-integration; no template property (C) | `orders.DataDTO.shippingMethod` → `ShippingMethodDTO.name/fulfilmentCode` (B); `orders.OrderItemDTO.shipmentProvider` (B) |
| **Ship confirmation payload** | `tracking_number`, `carrier`, `packages[]{sku, quantity}`, timestamps | The WMS's report that the order (or part of it) physically shipped: tracking number, carrier, per-package contents, and when. | This is the payload the OMS forwards to the channel to trigger "shipped" — it must carry the external reference echo plus tracking, or the channel leg stalls. | `EXAMPLE.IWmsOrderService.orderStatusUpdate, response orderNumber / status / trackingNumber ← payload.awb_no / orderItems[]` (A) | `OrderStatusUpdateDTO` — `.orderNumber`, `.status`, `.wmsStatus`, `.trackingNumber`, `.orderItems` (A) |
| **Inventory sync keys** | `sku` + `warehouse_id`, `on_hand`, `available` | Stock levels per SKU per warehouse, pushed or pulled periodically. | Feeds available-to-sell per channel. | **Secondary item identifiers** | `barcode`, `lot_number`, `serial_number`, `expiry_date` | Physical identifiers used inside the warehouse (scanning, batch and expiry control, serial tracking). | Required for regulated/batch goods and returns matching; ride alongside the SKU but never replace it as the join key. | not found in the templates | `orders.OrderItemDTO.upc` / `.serialNumbers` (B); lot/expiry: not found in wms-integration-core |

> **Inverted flow — channel-arranged logistics.** When the marketplace owns shipping, the OMS never calls the carrier. The channel books its own carrier and *assigns* the tracking number; the OMS retrieves it and fetches the label as a **platform document**, and carrier milestones arrive **through the channel's webhooks**. On this path the correlation keys are the channel order ID + package ID; the tracking number is a downstream attribute, not a key you mint. Check which model (or both) the new system uses before designing the carrier leg.

## Property lineage — three chains verified in code (2026-08-08)

Read-through of real integrations (`tiktok-v2-integration`, `viettel-integration`, `fedex-integration`) confirms the dual-identifier handshake is implemented as **verbatim string copies + local persistence** — values are never transformed in mapping logic; names change only at DTO JSON-key boundaries.

**Seller SKU** — one value, three wire names: channel `seller_sku` → `TiktokV2OrderLineItemDTO.sellerSku` → Jackson-copied into the OMS create-order item `TiktokV2CreateOrderItemDTO.itemSku` (wire key stays `seller_sku`) → OMS → OMS→WMS payload key **`sku`** → `orders.OrderItemDTO.sku` (bound by `mapper.convertValue(payload, CreateOrderServiceParam.class)` in the param factory) → WMS request + persisted `WmsOrderItem.sku` → status back as `OrderItemStatusUpdateDTO.sku`; stock back as `StockUpdateDTO.sellerSku` (no `@JsonProperty` → wire key is literally **`sellerSku`**). So: `seller_sku` → `sku` → `sellerSku`. Where a WMS has its own internal SKU, the bridge is `WmsCustomORM.getWmsInventoryReferenceBySellerAndSku(...)`, never a rename.

**Order number** — channel order `id` → `TiktokV2CreateOrderDTO.orderNumber` (`@JsonProperty("id")`) published to OMS → OMS emits it to the WMS as `data.order_number` → `orders.DataDTO.orderNumber` → the Viettel request `order_number` via another straight `mapper.convertValue` (the merchant reference sent to the WMS **is** the OMS order number, verbatim), persisted locally as `WmsOrders.orderNumber`. The WMS webhook echoes `order_number` back → `OrderStatusUpdateDTO.orderNumber`; the line-level echo is **re-attached from the local DB**, not from the webhook (`OrderItemStatusUpdateDTO.lineItemId ← WmsOrderItem.marketplaceOrderItemId`). On the carrier leg the dual pair is persisted together at shipment creation: `CarriersCustomORM.saveOrder(orderId, logisticsPartnerCode, sellerId, trackingNumber, status, …, orderNumber, shipmentId)` (FedEx).

**Tracking number** — the carrier response's tracking number (FedEx falls back to `createOrderDataDTO.getTrackingNumber()` when the OMS already supplied one — **both directions are live in code**) → `UpdateShippingDetailsDTO.trackingNumber` (+ `masterTrackingNumber` for multi-parcel) → `GlobalUtility.publishShipmentDetails(...)` to OMS. On the channel leg, the OMS RTS payload arrives as `RTSDataDTO.trackingNumber` (tiktok-v2 falls back to `orderNumber` when it's empty), and the channel may return an **updated** tracking number that is re-published to OMS inside `RTSRequestDTO`/`ShippingDetailsDTO` — the channel-arranged direction from the inverted-flow note, observed in code.

**Package ID** — TikTok's `package_id` is persisted **per item code** at order-fetch time (`CustomORM.saveItemReference` → `ItemReference.referenceId`) and re-resolved at RTS time by item code, with a live TikTok `getPackageIds` API call as fallback — exactly the "ship calls key on package, not order" behaviour this doc claims.

> **Boundary caveat.** The OMS core (SelluSeller) is **not in the JPluger repo**. Every chain crosses it; what OMS persists and re-emits is inferred from the matching payload shapes on both sides of it — that hop stays grade (B) permanently from this workspace.

## The order's passport — what the OMS must persist

The OMS is the hub, so the survival kit lives there. Per order: channel identity + channel order ID, channel line-item IDs (with their semantics), channel package ID(s), seller SKU per line, the OMS internal ID, the external reference sent to the WMS **plus** the WMS-assigned IDs, warehouse ID, the merchant reference sent to the carrier **plus** the carrier waybill and carrier code, COD amount, an address snapshot with its update timestamp, per-hop status with event timestamps mapped to one canonical status model, and any reverse-flow IDs (cancel/return) linked back to the original. All IDs stored as strings; all consumers idempotent by the dual keys, with periodic pull-reconciliation as part of the contract — not a fallback.
